saveUninitialized: true	“Even if user just looks at the site, give them a session cookie.”
saveUninitialized: false	“Only give them a session cookie if they actually do something (like log in).”


Types of session expiry:
Fixed expiry	Session dies exactly after 10 min, no matter what.	Banking sites — they log you out strictly after 10 min.
Sliding expiry	If the user keeps using the site, the timer resets, so they stay logged in longer.	Gmail, Facebook — stay logged in as long as you’re active.

eg: Case 1 — Fixed expiry
Even if you keep browsing, at 10:10 you’re logged out.
✅ Secure
❌ Annoying for active users.

Case 2 — Sliding expiry
If you click something at 10:08, the timer resets:
→ new expiry = 10:18
→ If you click again at 10:15 → new expiry = 10:25

⚙️ So where does resave fit in?
Older session systems didn’t know the user was still active unless you explicitly saved the session again.
That’s what resave: true does:
“Every time the user sends a new request, save the session again (so the expiry resets).”
It gives you that sliding expiry behavior.
If you don’t want that, you just keep resave: false,
and the session will expire exactly after your maxAge time — even if user is still active.

resave:false: ipo,users site la endha activities panlanaa,session already irukardhee irukum
resave:true: for evry request,session refresh aagum,even anam req.session change aaglanaa kooda
💡 “Manually refresh expiry” = calling req.session.touch()
If you want to keep the session alive without changing any data, you can “touch” it:

req.session.touch();
This tells express-session:
“Hey, update the expiry timestamp on this session in the store — but don’t rewrite all the session data.”
Internally, the store will call its .touch() method (e.g., in connect-mongo), which updates the TTL in Mongo.

(err, user, info) → comes from the strategy after it finishes checking credentials.

You can think of it like:Verify credentials → done() → custom callback → optionally log in → serialize → session

1️⃣ Two ways to handle login with Passport
a) Simple redirect version
app.post('/login',
  passport.authenticate('my-login', {
    successRedirect: '/dashboard',
    failureRedirect: '/login'
  })
);


Passport runs your strategy first (LocalStrategy).

Strategy calls done(null, user) → user is passed internally.

Passport automatically calls req.logIn(user) for you.

Only after req.logIn does it call serializeUser to store the user in the session.

Then it performs the redirect.

b) Manual callback version
app.post('/login', (req, res, next) => {
  passport.authenticate('my-login', (err, user, info) => {
    if (err) return next(err);
    if (!user) return res.status(401).send(info?.msg || 'Invalid credentials');

    // Serialization happens here:
    req.logIn(user, (err) => {
      if (err) return next(err);
      res.send('Login success');
    });

  })(req, res, next);
});

Strategy runs → calls done(null, user) → your callback (err, user, info) runs.
Serialization hasn’t happened yet.
When you call req.logIn(user), Passport calls serializeUser(user, done) at that moment.
After serialization completes, the user is stored in the session, and the request is considered authenticated.

2️⃣ Key takeaway
serializeUser only runs when Passport logs the user into the session.
That happens:
Automatically in the simple redirect form.
Manually when you call req.logIn(user) in the custom callback.
The (err, user, info) callback is called before serialization.

NOTE:
3. Why doesn’t deserializeUser run in the login request?
Even if you call Passport’s session middleware again in the same request:
It will NOT call deserializeUser
It will NOT populate req.user
Because the updated session is not yet saved until the request ends
👉 Passport is designed so that deserializeUser only runs at the beginning of a new request.

Every .find(), .sort(), .limit() modifies the same query object.
Even if you write:
Product.find().find({a:1}).find({b:2}).sort().limit()

Not multiple.

All .find() calls run line-by-line, but they only build/modify the query
✔ Only the final combined query is executed
✔ DB hit occurs just once

notes:
Why do we need next() if it’s just a function?”

Because pre-save hooks are middleware inside Mongoose — they work just like Express middleware:
Mongoose pauses the save() operation…
…runs your pre("save") hook…
…and waits for you to say: “Ok, continue!” → that’s next()
If you don’t call next() (or return a Promise):
Mongoose thinks your middleware is still running
So save() never finishes
Your code may freeze / never insert data into DB


Do update and delete create new objects and assign to variables?
Yes → for findOneAndUpdate() and findOneAndDelete()
No → for updateOne(), updateMany(), deleteOne(), deleteMany()
Same object reused → for save()

2. error handling middlewares (err,req,res,next) //specified err at first

puttig return only breaks the current middleware,

putting error object next(err) , only triggers all error handling middlewares, without executing normal middlewares
